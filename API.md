# Octopus Intelligent Go / SmartFlex API Notes

These notes document the unofficial Kraken GraphQL API surface observed from the
Octopus Energy Android app. The API is not public and can change without notice,
so Home Assistant entities should be implemented defensively and only enabled
when a device exposes the required fields.

The public integration name is **Octopus Intelligent Go** because that matches
the customer-facing EV charging product. The Kraken GraphQL schema and operation
names use **SmartFlex**, so API examples keep the original SmartFlex names.

## Endpoint

```text
https://api.oees-kraken.energy/v1/graphql/
```

Requests are HTTP `POST` calls with a JSON GraphQL body:

```json
{
  "query": "...",
  "operationName": "OperationName",
  "variables": {},
  "extensions": {
    "clientLibrary": {
      "name": "apollo-kotlin",
      "version": "5.0.0"
    }
  }
}
```

Useful headers observed from the Android app:

```text
x-apollo-operation-name: <operationName>
authorization: <access-token>
accept: multipart/mixed;deferSpec=20220824, application/graphql-response+json, application/json
accept-language: en-US
user-agent: OctoAppClient/Android/4.134.0 (Android 16; emu64a)
content-type: application/json
```

Login requests also include `x-kraken-flapjack`. The integration generates a
random hex value when one is not supplied.

## Authentication

Kraken uses `Login` for API-key, refresh-token, organization-secret, and
pre-signed-key authentication:

```graphql
mutation Login($input: ObtainJSONWebTokenInput!) {
  obtainKrakenToken(input: $input) {
    __typename
    refreshExpiresIn
    refreshToken
    token
  }
}
```

Supported input shapes in the current `api.oees-kraken.energy` schema:

```json
{"email": "user@example.com", "password": "..."}
{"APIKey": "sk_live_..."}
{"refreshToken": "..."}
{"organizationSecretKey": "..."}
{"preSignedKey": "..."}
```

The integration uses `email` and `password` only for initial setup or explicit
reauthentication. It discards the password immediately after Kraken returns a
refresh token. It then reads `viewer.liveSecretKey`. If that field is null, an
account with the `CAN_VIEW_API_KEY` permission can create a key with
`regenerateSecretKey`. The mutation returns the new key and subsequent viewer
queries expose the same value. Setup and reauthentication persist this key in
the Home Assistant config entry.

The returned `token` is the access token used in the `authorization` header. The
returned `refreshToken` can be exchanged with the same `Login` mutation to obtain
a fresh access token. On the Spain endpoint, normal user and API-key logins
currently return refresh tokens with a fixed seven-day lifetime.
`refreshExpiresIn` is an absolute Unix timestamp, not a duration. Exchanging the
refresh token does not rotate it or extend that expiration time. Once it expires,
the integration falls back to the stored API key and obtains a new token pair.

Long-lived refresh tokens are generated by authenticating with the app
organization token and passing the user access token:

```graphql
mutation generateLongLivedRefreshToken($input: ObtainLongLivedRefreshTokenInput!) {
  obtainLongLivedRefreshToken(input: $input) {
    __typename
    refreshToken
    refreshExpiresIn
  }
}
```

Kraken restricts this mutation to approved third-party organizations, so a
personal integration cannot use it without an organization secret. The durable,
revocable account API key is therefore the supported recovery credential for
this integration. Authentication operations remain serialized so overlapping
entity updates cannot race. Treat API keys and tokens as secrets and do not
commit them.

## Core Model

The SmartFlex API is not Tesla-specific. It is centered on account-scoped
SmartFlex devices:

- `accountNumber`: Octopus account identifier.
- `deviceId`: Kraken SmartFlex device identifier.
- `deviceType`: device category, for example `ELECTRIC_VEHICLE`.
- `provider`: integration provider, for example `TESLA`.
- GraphQL inline fragments expose type-specific data such as `SmartFlexVehicle`,
  `SmartFlexChargePoint`, `SmartFlexInverter`, and `SmartFlexHeatPump`.

Account discovery:

```graphql
query GetAccountList {
  viewer {
    __typename
    accounts {
      __typename
      number
    }
  }
}
```

Device discovery:

```graphql
query GetSmartFlexDevices($accountNumber: String!, $deviceId: String) {
  devices(accountNumber: $accountNumber, deviceId: $deviceId) {
    __typename
    id
    name
    deviceType
    provider
    propertyId
    integrationDeviceId
    status {
      __typename
      current
      isSuspended
    }
    preferences {
      __typename
      gridExport
    }
    ... on SmartFlexVehicle {
      make
    }
  }
}
```

## MVP Home Assistant Scope

For the first implementation, expose only these entities:

| Entity | Home Assistant type | API operation | Field/action |
| --- | --- | --- | --- |
| Target/max charge percentage | `number` | `GetSmartFlexDevicePreferences`, `SetSmartFlexDevicePreferences` | Read/write schedule `max` percentage |
| Immediate charging | `switch` | `GetSmartFlexDeviceState`, `FlexUpdateBoostCharge` | On writes `BOOST`; off writes `CANCEL` |
| Smart charging | `switch` | `GetSmartFlexDevicePreferences`, `UpdateDeviceSmartControl` | On writes `UNSUSPEND`; off writes `SUSPEND` |
| Start Immediate Charge | service | `FlexUpdateBoostCharge` | Always write `action: BOOST` |
| Cancel Immediate Charge | service | `FlexUpdateBoostCharge` | Always write `action: CANCEL` |
| Current charging/device state | `sensor` | `GetSmartFlexDeviceState` or `GetSmartFlexDevicesStates` | `status.currentState` |
| Current state of charge | `sensor` | `GetSmartFlexDeviceChargeCapability` | `status.stateOfCharge.value` |
| Current vehicle charge limit | `sensor` | `GetSmartFlexDeviceChargeCapability` | `status.stateOfChargeLimit.upperSocLimit` |

Use capability-based setup. For example, only create the state-of-charge sensor
when the device response contains `SmartFlexVehicle.status.stateOfCharge`.

## MVP Operations

### Read Preferences

```graphql
query GetSmartFlexDevicePreferences($accountNumber: String!, $deviceId: String) {
  devices(accountNumber: $accountNumber, deviceId: $deviceId) {
    __typename
    id
    preferences {
      __typename
      targetType
      unit
      mode
      gridExport
      schedules {
        __typename
        dayOfWeek
        time
        min
        max
        upperLimit
      }
      isChargingDurationCapped
    }
  }
}
```

For EV charging, the captured write path uses:

```json
{
  "input": {
    "deviceId": "<device-id>",
    "mode": "CHARGE",
    "unit": "PERCENTAGE",
    "schedules": [
      {"dayOfWeek": "MONDAY", "time": "07:30", "max": 69.0}
    ]
  }
}
```

### Set Target Charge Percentage

```graphql
mutation SetSmartFlexDevicePreferences($input: SmartFlexDevicePreferencesInput!) {
  setDevicePreferences(input: $input) {
    __typename
    id
    preferences {
      __typename
      targetType
      unit
      mode
      schedules {
        __typename
        dayOfWeek
        time
        min
        max
      }
    }
  }
}
```

The current integration writes the same `max` value for all seven weekdays.

### Start or Cancel Immediate Charging

```graphql
mutation FlexUpdateBoostCharge($input: UpdateBoostChargeInput!) {
  updateBoostCharge(input: $input) {
    __typename
    id
    provider
    deviceType
  }
}
```

Start immediate charging:

```json
{"input": {"deviceId": "<device-id>", "action": "BOOST"}}
```

Cancel immediate charging:

```json
{"input": {"deviceId": "<device-id>", "action": "CANCEL"}}
```

### Suspend or Resume Smart Charging

The Spain schema and a live Spain account expose this operation. The integration
uses it for the Smart charging switch:

```graphql
mutation UpdateDeviceSmartControl($input: SmartControlInput!) {
  updateDeviceSmartControl(input: $input) {
    __typename
    id
    status {
      __typename
      isSuspended
    }
  }
}
```

Suspend SmartFlex planning and charging:

```json
{"input": {"deviceId": "<device-id>", "action": "SUSPEND"}}
```

Resume SmartFlex control:

```json
{"input": {"deviceId": "<device-id>", "action": "UNSUSPEND"}}
```

`status.isSuspended` is the readback state. This controls Kraken SmartFlex; it
does not override charging initiated independently by the vehicle or charger.
An active boost may also need to be cancelled separately.

### Read Device State

Single device:

```graphql
query GetSmartFlexDeviceState($accountNumber: String!, $deviceID: String!) {
  devices(accountNumber: $accountNumber, deviceId: $deviceID) {
    __typename
    id
    status {
      __typename
      currentState
    }
  }
}
```

All devices for an account:

```graphql
query GetSmartFlexDevicesStates($accountNumber: String!) {
  devices(accountNumber: $accountNumber) {
    __typename
    id
    status {
      __typename
      currentState
    }
  }
}
```

### Read Vehicle Charge Capability

```graphql
query GetSmartFlexDeviceChargeCapability($deviceId: String, $accountNumber: String!) {
  devices(deviceId: $deviceId, accountNumber: $accountNumber) {
    __typename
    id
    ... on SmartFlexVehicle {
      chargePointPowerOutput
      vehicleBatterySize
      status {
        __typename
        ... on SmartFlexVehicleStatus {
          stateOfCharge {
            __typename
            value
          }
          stateOfChargeLimit {
            __typename
            upperSocLimit
          }
        }
      }
    }
    ... on SmartFlexChargePoint {
      chargePointPowerOutput
      vehicleBatterySize
    }
  }
}
```

For the MVP, use only:

- `stateOfCharge.value`
- `stateOfChargeLimit.upperSocLimit`

## Later Candidate Data Points

These were found in the Android app but should stay out of the first release:

| Area | Operation | Possible entities/data |
| --- | --- | --- |
| Preference constraints | `GetSmartFlexDevicePreferenceSettings` | min/max allowed values, time step, schedule ranges |
| Planned charging | `FlexPlannedDispatches` | next dispatch start/end, type, expected kWh |
| Charge history | `GetSmartFlexChargeHistory` | session start/end, energy, cost, final SoC, charge problems |
| Alerts | `GetSmartFlexDeviceAlerts` | alert messages and publish timestamps |
| Charge duration cap | `UpdateDeviceIsChargingDurationCapped` | enable/disable duration cap |
| Grid export | `UpdateDeviceGridExport` | export preference |
| Re-auth status | `GetDeviceReAuthenticationState` | re-auth eligibility/required flow hints |
| Charge point metadata | `GetSmartFlexChargePointDevices` | charger make/model/status |
| Inverter telemetry | `GetSmartFlexInverterTelemetry`, `InverterLiveTelemetry` | solar, grid, site, battery, inverter power |
| Heat pump telemetry | `GetSmartFlexHeatPumpTelemetry`, Daikin operations | temperatures, modes, hot water/climate control |
| Legacy battery telemetry | `GetLegacyBatteryTelemetryQuery` | battery SoC, import/export limits, power readings |

Avoid implementing onboarding and deauthentication flows until there is a clear
product need. They affect account/device linking and are higher risk than normal
read/control entities.

## Discovering New Data Points

Use two complementary methods: capture the app traffic and inspect the generated
GraphQL operation strings inside the APK.

### 1. Capture App Traffic

1. Patch the Android app so it trusts user-installed CAs.
2. Install the proxy CA certificate on the emulator/device.
3. Set the emulator/device HTTP proxy to mitmproxy or Burp.
4. Perform the action in the app.
5. Save the GraphQL request body, `operationName`, variables, and response.

Important things to preserve:

- `operationName`
- exact GraphQL `query`
- variable names and enum values
- response shape
- whether the operation requires an account number, device ID, property ID, or
  other context

Redact tokens, email addresses, account numbers, and device identifiers before
committing captures.

### 2. Extract GraphQL Operations From the APK

After decoding the APK with apktool, the generated Apollo/Kotlin operation
classes contain the GraphQL documents as string constants.

Useful searches:

```bash
rg -uu -n 'const-string p0, "(query|mutation).*SmartFlex' \
  <decoded-apk>/smali_classes*/tech/kraken/mobile/sdk/graphql/generated
```

```bash
rg -uu -n 'const-string p0, "(query|mutation).*Charge' \
  <decoded-apk>/smali_classes*/tech/kraken/mobile/sdk/graphql/generated
```

```bash
rg -uu -n 'const-string p0, "(query|mutation).*Telemetry' \
  <decoded-apk>/smali_classes*/tech/kraken/mobile/sdk/graphql/generated
```

To inspect a specific generated operation:

```bash
nl -ba <decoded-apk>/smali_classes6/tech/kraken/mobile/sdk/graphql/generated/plugins/smartflex/GetSmartFlexDeviceChargeCapabilityQuery\$a.smali
```

The operation string is usually near a method returning `Ljava/lang/String;`.

### 3. Validate Before Exposing in Home Assistant

For each new data point:

1. Confirm the operation exists in the APK or in a live app capture.
2. Run it against a real account with a temporary client method.
3. Record the response for at least one supported device.
4. Decide whether the field is read-only, writable, or diagnostic.
5. Add Home Assistant entities only when the device response includes the
   required fields.
6. Handle missing fields as unsupported capability, not as an error.

## Implementation Notes

- Poll read-only sensors conservatively. Start with a 60-120 second interval for
  device state and SoC unless the API proves it can handle faster polling.
- Use one shared coordinator per account/device to avoid duplicate GraphQL calls.
- Keep writes explicit: Home Assistant services/switches should call mutations
  only when the user or automation requests them.
- Do not store the account password. Store the refresh token and revocable API
  key in Home Assistant's config entry data. Read the existing viewer key before
  generating one so setup does not rotate a valid account key.
- Keep access tokens and refresh tokens out of logs.
